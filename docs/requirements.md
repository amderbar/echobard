# requirements.md

echobard の要件をまとめる。実装が進むにつれて更新する前提のドキュメント。

## 1. 背景・目的

詩歌(短歌・俳句・古典詩歌など)をお題にしたタイピングゲームを作る。
IME や音声入力を含む多様な入力方式を前提とし、「入力確定後の文字列」を判定対象とすることで、
入力方式そのものを競技の対象にしない設計とする。

既存の歌詞タイピングゲームの多くはローマ字入力・打鍵速度を前提としており、
IME 確定後判定 × 詩歌という組み合わせは類例が見当たらなかった
(2026-08 時点の調査。[ADR-0001](adr/0001-project-kickoff.md) 参照)。

## 2. スコープ

### 2.1 対象とする入力方式

- 物理キーボード(日本語 IME・英語配列など)
- モバイル端末のソフトウェアキーボード(フリック入力含む)
- 音声入力

いずれの方式も **区別せず許容する**。入力方式の検知・制限は行わない
(判断の経緯は今後 ADR として記録予定)。

### 2.2 対象とするお題

- 初期実装では日本語の詩歌(和歌・俳句など)を中心に収録する。
- データ構造・判定ロジックは日本語に限定せず、将来的に他言語・他文字体系
  (英詩、漢詩、ハングルなど)や散文を扱えることを設計上の制約とする。

### 2.3 スコープ外(現時点)

- マルチプレイヤー・対戦要素
- ランキング・全国スコア共有
- 音声入力の検知・無効化
- 詩歌以外のお題ジャンルの本格収録

## 3. 機能要件

### 3.1 セッション進行

- 1 行(一首・一句などの区切り単位)を 1 問として、行ごとに進行する。
- 各行について「入力 → 確定 → 採点 → 次の行」のサイクルを繰り返す。

> **(暫定)** 「詩歌 1 首(または 1 篇)を 1 セッションの単位とし、全行終了時に合計スコアを
> 表示する」という区切り方は、コードの検討過程で出てきた形をそのまま書き起こしたもので、
> 明示的に合意した仕様ではない。1 セッションの範囲(1 首単位か、複数首をまとめて 1 セッション
> にできるかなど)は未決事項として改めて確認する。

### 3.2 入力・確定

- 入力欄への最初の文字入力をもって「入力開始」とする。
- 確定操作(Enter/Done キー相当)をもって「入力確定」とし、その時点の文字列を判定対象とする。
- 確定時、直前の入力から変化がない場合や空文字列の場合は誤送信とみなしガードする。
- 明示的な送信ボタンは初期実装では設けない。運用の中で確定操作の挙動に問題が出た場合、
  送信ボタンの追加を検討する(判断の経緯は今後 ADR として記録予定)。

### 3.3 採点

- **一致度**: 確定文字列とお題文字列の編集距離(レーベンシュタイン距離)をもとに算出する。
  文字列比較の前に、全角/半角・句読点表記ゆれなどの正規化を行う。
  お題によっては送り仮名・異体字の別解(`alt_matches`)を許容する。
- **時間スコア**: 入力開始から確定までの経過時間を、お題の文字数に応じた目標時間との比で算出する。
- **合成スコア**: 一致度を主、時間を従とした重み付けで合成する。重み比率の具体的な数値
  (例として挙がったのは一致度 0.7 : 時間 0.3)は未決事項であり、調整可能なパラメータとして
  持たせる方針のみ確定している。
- 行ごとのスコアを記録し、複数行分を集計する方法(単純平均か文字数による重み付けか)は
  未決事項とする。

### 3.4 お題データ

- お題(詩歌)は JSON/TOML などの外部データとして保持し、コード変更なしで追加できるようにする。
- 1 つの詩歌は複数行(`Line`)から構成され、各行は表示用テキスト・読み仮名・別解表記を持つ。
- 出典(作者・歌集・時代など)をメタデータとして保持する。

## 4. 非機能要件

### 4.1 アーキテクチャ

- ロジックは `echobard-core`(Godot 非依存の Rust クレート)と `echobard-ext`(gdext を用いた
  Godot ブリッジ)に分離する。クレートの配置(ワークスペース直下にフラット)は `slide-roguelike`
  の構成方針を踏襲する。
- Godot プロジェクトのディレクトリ名は `godot/` とする。`slide-roguelike` はリポジトリ名と
  同名のディレクトリに Godot プロジェクトを置いているが、echobard では役割が伝わる名前を
  優先し変更している(経緯は [ADR-0002](adr/0002-directory-layout.md) を参照)。
- `echobard-core` はテスト容易性・移植性を優先し、Godot API に依存する処理を含めない。
- デスクトップ向けのビルド成果物(`target/debug/` 以下)は Godot プロジェクト内に
  コピーせず、`.gdextension` から相対パスで直接参照する。Android のみ、Godot プロジェクト
  内(`libs/android/`)にライブラリを同梱する(`slide-roguelike` の方式を踏襲)。

### 4.2 プラットフォーム

- Godot によるマルチプラットフォーム対応を前提とする(デスクトップ・モバイル)。
- モバイル(特に Android/iOS)では、仮想キーボード表示時のレイアウト崩れを防ぐ。

### 4.3 データ管理・ライセンス

- コードのライセンスは MIT(将来的に MIT OR Apache-2.0 のデュアルライセンス化を検討)。
- お題データはコードと別にライセンス・出典管理を行う。初期収録はパブリックドメイン作品を
  中心とし、著作権が存続する作品を収録する場合は許諾状況を明記する。

## 5. 未決事項

- セッションの区切り方(詩歌 1 首を 1 セッションとするか、複数首をまとめられるか等)
- 合成スコアの重み付け(一致度:時間の比率)の最終値
- 行スキップ・やり直し操作の要否
- 複数行分のスコア集計方法(単純平均 / 文字数重み付け)
- 送信ボタンの要否(実機検証待ち)
- お題データの正規化ルール(表記ゆれ・異体字の許容範囲)の詳細

決まったものから、決定の経緯を ADR として `docs/adr/` に記録していく
(運用方針は [docs/adr/README.md](adr/README.md) を参照)。
