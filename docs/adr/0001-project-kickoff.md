# ADR-0001: プロジェクト開始と初期案、リポジトリ名の決定

- Status: Accepted
- Date: 2026-08-08

## Context

詩歌をお題にしたタイピングゲームを作りたい、という発想からプロジェクトを開始した。
着想の時点で以下の要素が既に固まっていた。

- IME・予測変換・音声入力など、入力方式は問わない。
  判定は「入力確定後の文字列」と「期待文字列」の比較で行う。
- スコアは「入力開始から確定までの時間」と「文字列の一致度」の複合評価とする。
- ゲームエンジンは Godot、コアロジックは gdext を用いて Rust で実装する。
  この構成方針は既存プロジェクト `slide-roguelike`(`core`/`ext` クレート分離)を踏襲する。
- お題は詩歌を中心に据えるが、文字種・言語を限定しない設計とする。

開発着手にあたり、(1) 開発を始めること自体の決定、(2) 設計の初期案の記録、
(3) リポジトリ名の決定、の 3 点を最初の ADR として残す。

## Decision

### 1. 開発を開始する

上記コンセプトのもと、新規プロジェクトとして開発を開始する。
既存の類似ゲームを調査したが、「詩歌」「IME 確定後判定」「時間 × 一致度スコア」を
組み合わせたゲームは見当たらず、空いているポジションと判断した
(既存の歌詞タイピングゲームはローマ字入力・打鍵速度を前提としたものが中心で、
短歌・俳句アプリは創作・投稿 SNS が主目的であり、いずれも今回のコンセプトとは異なる)。

### 2. 初期設計案

以下を初期設計方針として採用する。詳細は [requirements.md](../requirements.md) に記録する。

- **入力判定**: `LineEdit` の `text_submitted`(確定操作)で判定する。送信ボタンは設けず、
  キーボード側の確定操作(Enter/Done キー)に委ねる。誤送信防止のガードのみ実装する。
  運用上問題が出た場合は送信ボタンの追加を検討する。
- **入力方式の扱い**: モバイルでの音声入力は技術的に検知・区別ができないため、
  検知・制限を行わず許容する方針とする。
- **セッション進行**: 詩歌 1 行(一首・一句)を 1 問とし、行ごとに「入力 → 確定 → 採点」の
  サイクルを繰り返す。
- **スコアリング**: 一致度はレーベンシュタイン距離ベースで算出し、全角/半角や句読点の
  表記ゆれを正規化した上で比較する。時間スコアはお題の文字数に応じた目標時間との比で算出する。
  一致度を主、時間を従とした重み付けで合成する。
- **アーキテクチャ**: `echobard-core`(Godot 非依存の Rust クレート)と `echobard-ext`(gdext ブリッジ)
  に分離する。`slide-roguelike` と同じ構成方針を踏襲する(詳細は [ADR-0002](0002-directory-layout.md) 参照)。
- **お題データ**: JSON/TOML で外部化し、コード変更なしで追加できるようにする。

### 3. リポジトリ名: `echobard`

以下の案を検討した。

| 案 | 採用しなかった理由 |
|---|---|
| `typoet`(typewriter + poet のもじり) | 既存の同名タイピングゲームプロジェクトが GitHub 上に存在し、ジャンルが重複するため回避した |
| `kotodama`(言霊) | 単語の含意が重すぎる(呪術性・霊力のニュアンス) |
| その他和語案(`utayomi` など) | プロジェクトは日本語の詩歌に限定しない設計方針のため、リポジトリ名を日本語前提にしたくない |

最終的に `echobard` を採用した。「お題の言葉をこだま(echo)のように打ち返す」という
ゲーム体験と、「詩歌を詠む者(bard)」のイメージを組み合わせた造語である。
`typewriter` の "writer" を "bard" に置き換える発想は、`typoet` の際の
「type + 行為者」という言葉遊びの構造を引き継いでいる。
既存の "echobard" 使用例(オーディオ機器レビューサイト、音楽チャンネルなど)を確認したが、
いずれも別ジャンルであり、ソフトウェア分野での衝突は確認されなかった。

リポジトリは `https://github.com/amderbar/echobard` としてパブリックで作成し、
ライセンスは MIT を選択した(将来的に `MIT OR Apache-2.0` のデュアルライセンス化を
検討の余地として残す)。

## Consequences

- 入力方式を限定しない設計により、将来的に自前ソフトウェアキーボードなどで
  厳密な入力方式の検証を行いたくなった場合、別途大きな設計変更が必要になる
  (現時点ではスコープ外と割り切る)。
- リポジトリ名・プロジェクト名が日本語の言葉遊び(typewriter のもじり)を由来としつつ
  英語の造語になっているため、由来自体は説明なしには伝わらない
  (README にコンセプトとして簡潔に記載する)。
- お題ジャンルを詩歌・多言語に開いたままにしているため、初期実装(日本語の詩歌)と
  将来の拡張(他言語・散文)の境界を要件定義側で明確にし続ける必要がある。
