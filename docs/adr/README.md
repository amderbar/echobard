# Architecture Decision Records (ADR)

このディレクトリには、echobard の設計・実装における重要な決定とその経緯を記録する。

## 目的

- 「なぜその設計にしたか」を後から追えるようにする。
- 一度検討して却下した案を再検討する手間を省く。
- 開発者が自分自身であっても、時間が経てば文脈を忘れる前提で記録する。

## ADR を書くとき / 書かないとき

**書く**

- 複数の選択肢を比較検討した上で、後から覆すコストが小さくない決定をしたとき
  (例: アーキテクチャの分割方針、入力判定の方式、公開範囲やライセンスの決定)
- 一度は採用しかけて却下した案があり、その理由を残す価値があるとき

**書かない**

- パラメータの具体的な数値(重み付けの比率など)や、実装の仕様レベルの詳細
  → `requirements.md` や該当コードのコメント・ドキュメントコメントに書く
- 気軽に覆せる実装の細部

迷ったら、「半年後の自分がこの決定を見て、なぜそうしたか分からず困りそうか」を基準にする。

## ファイル命名・番号

`NNNN-短いタイトル.md` の形式とする(例: `0001-project-kickoff.md`)。

- `NNNN` は 4 桁の連番。**採番は決定した順**(検討を始めた順ではない)。
- 番号は欠番・重複なく振ること。一度採番したファイルの番号は変更しない。
- 既存の決定を覆す場合も新しい番号の ADR を起こす(既存の ADR は削除・上書きしない。
  「Status」を `Superseded by ADR-XXXX` に更新する)。

## フォーマット

[`0000-template.md`](0000-template.md) をコピーして使う。最低限、以下を含める。

- **Status**: `Proposed` / `Accepted` / `Superseded by ADR-XXXX` / `Deprecated` のいずれか
- **Context**: なぜこの決定が必要になったか、前提や制約
- **Decision**: 何を決めたか。検討した他の選択肢とその却下理由も含める
- **Consequences**: この決定によって生じる影響・トレードオフ・今後の課題
